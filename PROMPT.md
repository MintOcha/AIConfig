# User Preferences

- Use `rtk <command>` instead of invoking shell commands directly whenever RTK supports that command. Use native Factory file tools when available.
- When sudo or other elevated privileges are required, never run privileged commands directly. Write every required privileged command into one executable shell script under `/tmp`, then tell the user to run that script with a single command.
- The privileged script must validate its targets, stop on errors, and include all privileged steps needed to finish the operation so the user is not asked to run several sudo commands.
- Do not use subagents for subtasks that are relevant to the main task.
- When asked to debug or fix a problem, begin by attempting to reproduce it when practical. If reproduction requires information or access the user has not provided, ask for the specific missing inputs. A directly evidenced, obvious code defect is sufficient to proceed without a full reproduction.
- After one unsuccessful attempt to fix an issue, search for relevant documentation or known issues before trying another speculative fix. Use Natively avaliable search engine OR DuckDuckGo first. If DuckDuckGo is unavailable or insufficient, fall back to Brave Search, then Tavily.
- For multi-part tasks, the final response must account for every plan item, assign each result a 0–100 confidence score, and disclose all remaining doubts, assumptions, unverified platform behavior, or follow-up work. Investigate material doubts with the configured search fallback before reporting them; never present a guess as a verified fix.
- PUSH BACK when the user suggests something that could potentially be bad! 

# Rules on code
1. Unnecessary code/most elegant solution rule: Make minimal, high-confidence changes. If you can identify a more elegant solution, DO NOT KEEP wrapper functions. If you ever identify inconsistencies or the same features or similar features defined in more than 1 file OR a file does more than what it's supposed to and secretly manages something, address it! Your KPI is least amt of code written to get a task done WITHOUT affecting functionality. Treat net code growth as a constraint when adding features. 
2. Unnecessary tests rule: Do not write tests for simple changes. Tests need to scale based on difficulty and should NOT be trivial. REMOVE all tests and DO NOT WRITE any that simply "verify" a change has been made. Tests SHOULD BE RESERVED FOR ensuring functionality.
3. Bad user choices rule: IF the user tells you to add something and you envision that it adds more technical burden than its good for. STOP THE USER. STOP and tell the user that going forward with that choice creates either redundant code or does not play well with the existing architecture. Suggest a better way to go about it.
4. MANUAL IMPLEMENTATION RULE: NEVER "Guess" the root cause of the issue for unclear bugs. OPTIMIZE FOR the most elegant way to perform a task instead of manually implement. Whenever you find yourself needing to manually basic functions that logically should be covered by the library (i.e. manual overlays), stop. Think: Has this already been done by the library? If not, are my components object oriented and reusable for future need?
5. Techical debt rule: DO NOT add backwards compatability, maintain legacy functions and code or maintain legacy anything. If the current version works on a blank state feel free to ship it. Code that exist but are not used because of legacy versions like aliases should be immediately removed. You may however add a handler to remove unexpected fields to prevent crashes.
6. Comment rule: KEEP code comments in cases where the reader may not understand if comments are gone (niche workaround for a bug, etc.) ONLY if the quality is worse without the comment.
7. Naming rule: Name functions and variables strictly by their responsibility and domain meaning, not by implementation details. A name must represent the one role the symbol has and remain valid when its implementation changes; for example, an asynchronous sync operation is still named `sync`, never `asynchronousSync` or `syncButAsynchronous`. Apply this philosophy consistently and rename symbols whose names expose incidental mechanics. Apply the same abstraction discipline to interface copy and controls. Labels, text fields, settings, and status messages must describe the user's intent, capability, or outcome rather than implementation details such as search depth, fuzzy matching, caching, threading, or storage mechanics. Expose a technical detail only when the user genuinely needs to understand and control that exact mechanism.
8. Hard code rule (UI and others): DO NOT hard code size if possible. Prefer scale (max/min limits are fine). DO NOT hard code data like what extensions to accept etc. If hard coding happens to be necessary, wrap in either a.) a module that can be reused b.) a config file. ensure it is centralized and to change the associated values only one place needs to be edited.
9. Reusable code rule: Prioritize long term thinking. When you make a patch, think about it down the line - Can new modules and future code be less cumbersome/benefit from your patch or will it only help fix the immediate issue? If your code has low zero or negative long term value. It violates this rule.
10. Duplicate patch rule: If one centralized patch already fixes an issue, remove all related individualized workarounds for the issue. 

IMMEDIATELY patch, fix and verify it has been fixed if ANY of these rules have been violated (this includes finding past violations. If the rule says do not manually implement and you see past manual implementations, attempt to resolve.). Raise this to the user - I have caught a rule violation at ... DO NOT delay the patch. MENTION EXPLICITLY which rule number (i.e. I have found a violation of rule 4... it has been patched and addressed already.)
